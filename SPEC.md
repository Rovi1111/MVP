Ты — senior Python-разработчик. Сервис будут реально использовать в компании, поэтому важны корректность расчётов, понятные ошибки и поддерживаемый код.

## 1. Контекст и границы MVP

Аналитическая платформа: принимает данные о расходах, строит дашборд, сравнивает периоды и факт с бюджетом, выдаёт AI-анализ и рекомендации. На её основе корректируется бюджет организации.

**В MVP:**
- Данные факта и бюджета поступают только через drag&drop Excel/CSV (и ручной ввод формой/JSON).
- Вход по собственным логинам/паролям (не Active Directory).
- Запуск локально на MacBook (Apple Silicon).

**НЕ делаем сейчас, но закладываем архитектуру:**
- Интеграции по API (банк, эквайринг, 1С/ERP, корпоративные карты, Budget API). Нужен абстрактный интерфейс источника данных (`DataSource`) с одной реализацией `ExcelSource`, чтобы позже добавить API-коннекторы без переписывания логики.
- Аутентификация через Active Directory/LDAP — оставить точку расширения в слое auth.

## 2. Стек

- Python 3.12, FastAPI, Pydantic v2
- SQLAlchemy 2 + Alembic, база **SQLite** (код без SQLite-специфики, чтобы потом переключиться на PostgreSQL одной строкой в конфиге)
- UI: Jinja2 + **HTMX** (частичное обновление страниц без отдельного фронтенд-проекта), минимальный CSS без тяжёлых фреймворков
- pandas + openpyxl для чтения/записи Excel
- Plotly для графиков, kaleido для экспорта в PNG
- PDF: выбери библиотеку, которая ставится на macOS без системных зависимостей (например ReportLab), и обоснуй
- httpx для запросов к Ollama
- Хеширование паролей: argon2 или bcrypt; сессии — подписанные httpOnly cookie; CSRF-защита форм
- pytest для тестов; ruff для линтинга
- Управление зависимостями: uv (или venv + requirements.txt)

Ollama запускается нативно на Mac (не в Docker — в Docker на Mac нет GPU), по умолчанию `http://localhost:11434`, модель `llama3.1`.

## 3. Архитектура

- **API-first:** вся бизнес-логика доступна через REST (`/api/...`, JSON). Веб-страницы (`/web/...`) — тонкий слой поверх тех же сервисов.
- Слои: `models` (ORM) → `repositories` → `services` (чистая бизнес-логика, без FastAPI) → `api` и `web` роутеры.
- Расчёты сравнения и план-факта — чистые функции, покрытые unit-тестами.
- Все запросы к данным фильтруются по `org_id` текущего пользователя (изоляция организаций). Это проверяется тестом.
- Настройки через `.env` + таблица настроек в БД (для того, что меняет администратор в UI).

## 4. Роли и права

Три роли: **Администратор**, **Руководитель**, **Базовый сотрудник**. Каждая роль видит только разрешённые разделы и действия (пункты меню и кнопки скрываются, а сервер дополнительно проверяет права — 403 при попытке обхода). Матрицу прав держи в одном месте в коде.

|---|---|---|---|
| Управление пользователями и ролями | ✅ | — | — |
| Загрузка факта/бюджета из файла | ✅ | — | ✅ |
| Ручной ввод данных (форма/JSON) | ✅ | ✅ | ✅ |
| Справочник категорий и ЦФО (CRUD), ручное сопоставление статей | ✅ | ✅ | — |
| Сравнение периодов, план-факт, дашборд, фильтры | ✅ | ✅ | ✅ |
| Запуск AI-анализа | ✅ | ✅ | ✅ |
| Отчёты: просмотр, экспорт PDF/Excel, отправка на email | ✅ | ✅ | ✅ |

| Журнал действий (аудит) | ✅ | — | — |

Первый администратор создаётся CLI-командой (`python -m app.cli create-admin`).

## 5. Модель данных (ориентир, можно улучшить)

- `organizations`
- `users` (org_id, login, password_hash, role, is_active)
- `categories` — справочник статей расходов организации (name, is_active)
- `cost_centers` — ЦФО (name)
- `category_aliases` — сопоставление «название статьи из файла → категория» (запоминается после ручного сопоставления)
- `uploads` — каждая загрузка = новая версия (kind: fact | budget, file_name, uploaded_by, created_at, version, status)
- `expense_records` — факт (org_id, upload_id, period, category_id, cost_center_id nullable, amount, source)
- `budget_lines` — план (org_id, upload_id/версия бюджета, period, category_id, cost_center_id nullable, amount)
- `analyses` — сохранённые сравнения: параметры, снимок результатов (JSON), текст AI-анализа, автор, дата → можно вернуться к прошлым расчётам
- `prompt_templates` (name, scenario/role, text с плейсхолдерами)
- `settings` (ollama_url, ollama_model, ollama_timeout, порог отклонения план-факта, SMTP)
- `audit_log` (user, action, entity, details, timestamp)

**Периоды:** храним помесячно (первый день месяца). Сравнивать можно месяц, квартал, год или произвольный диапазон месяцев — данные агрегируются. На входе распознавать форматы `2025-01`, `01.2025`, `янв 2025`, даты Excel, `2025-Q1`/`1 кв 2025` (квартал без разбивки по месяцам — понятная ошибка или явное правило, предложи).

## 6. Загрузка данных

- Drag&drop зоны для **файла факта** и **файла бюджета** (отдельные), XLSX/XLS/CSV.
- Колонки факта: `Период`, `Статья` (категория), `Сумма`, `ЦФО` (необязательна). Бюджета: те же колонки, сумма = план.
- Распознавать синонимы колонок (рус/англ), как в `legacy/main.py`; CSV — автоопределение разделителя и кодировки (utf-8-sig, cp1251); суммы с пробелами и запятыми.
- Скачиваемые шаблоны Excel для факта и бюджета.
- **Валидация перед записью:** суммы — числа, категория — непустая строка, период распознан, обязательные поля заполнены. При ошибках показывать таблицу «строка — колонка — проблема» и ничего не записывать.
- Несколько строк одной категории за период суммируются.
- **Несопоставленные статьи:** если название не найдено в справочнике/алиасах — экран ручного сопоставления (выбрать существующую категорию или создать новую). Решение запоминается в `category_aliases`.
- Предпросмотр перед подтверждением загрузки (первые строки + итоги).
- Ручной ввод: форма (строки период/категория/сумма/ЦФО) и JSON-редактор с примером формата и валидацией.

## 7. Сравнение и план-факт

**Сравнение двух периодов** (period1, period2):
- Таблица по категориям: `amount_p1`, `amount_p2`, `delta = p2 − p1`, `pct_change`, `change_type`.
- `change_type`: `increase` (Рост), `decrease` (Снижение), `new` (Новая: 0 в p1, >0 в p2), `removed` (Исчезнувшая: >0 в p1, 0 в p2), `no_change` (Без изменений). В UI — русские названия, в API — английские коды.
- `pct_change` для `new` = n/a (без деления на ноль).
- Итоги за каждый период и общая дельта.
- Сортировка по delta по убыванию по умолчанию; новые и исчезнувшие категории визуально выделены.
- Фильтры: по названию категории, типу изменения, периоду, ЦФО.
- Если оба периода пустые — понятное сообщение об ошибке.

**План-факт** (за выбранный период/диапазон, версия бюджета — последняя или выбранная):
- По категориям (и ЦФО): план, факт, отклонение абсолютное и в %, флаг перерасхода.
- Порог значимого отклонения настраивается; превышения подсвечиваются.

## 8. Визуализация (дашборд)

- Круговая диаграмма распределения по категориям для **каждого** из сравниваемых периодов, с процентами.
- «Нет данных» вместо диаграммы, если данных нет или все суммы нулевые.
- Выбор категорий и диапазона сумм для диаграмм.
- Stacked bar по периодам (как в прототипе: доля категории в hover).
- График план-факта по категориям.
- Скачивание любой диаграммы в PNG (для презентаций).

## 9. AI-анализ (Ollama)

- Запускается кнопкой после сравнения/план-факта (асинхронно, с индикатором загрузки через HTMX). Автоматически — только если включено в настройках.
- В Ollama отправляются **только агрегаты** (итоги, топ ростов/снижений, новые/исчезнувшие, отклонения план-факта), не сырые строки.
- Содержание заключения: общий тренд; крупнейшие роста; крупнейшие снижения; новые и исчезнувшие категории; существенные отклонения от бюджета; 2–4 практические рекомендации. Язык — русский.
- Шаблоны промптов в БД, редактируются администратором, с плейсхолдерами. Минимум два шаблона из коробки: «для финансового аналитика / руководителя» (с финансовыми терминами) и «простым языком» (для владельца бизнеса без финансового образования). Пользователь выбирает шаблон при запуске.
- Текст сохраняется в `analyses`, кнопка «Скопировать».
- Ollama недоступна / таймаут → понятное сообщение в UI, остальной функционал работает.
- URL, модель и таймаут меняет администратор в UI.

## 10. Отчёты, экспорт, аудит

- Единый отчёт: параметры, сравнительная таблица, план-факт, диаграммы, AI-заключение.
- Экспорт в **PDF** (с диаграммами-картинками) и **Excel** (таблицы на листах, числа как числа).
- Отправка отчёта на указанный email через SMTP (настройки в `.env`/админке; если SMTP не настроен — кнопка неактивна с подсказкой).
- История: список прошлых загрузок (версии) и сохранённых анализов, можно открыть любой.
- Журнал аудита: вход/выход, создание/изменение/удаление данных, запуск AI-анализа, экспорт.

## 11. Этапы реализации

Приоритет требований: сначала отсекающие, затем критичные, затем желательные.

1. **Каркас:** структура проекта, конфиг, БД + миграции, модели, auth (логин/логаут, хеш паролей, сессии), роли и проверка прав, CLI create-admin, изоляция по org_id, базовый layout.
2. **Данные:** справочники категорий и ЦФО, загрузка факта и бюджета из Excel с валидацией и предпросмотром, сопоставление статей, ручной ввод (форма + JSON), версии загрузок.
3. **Расчёты:** сервис сравнения периодов и план-факта + исчерпывающие unit-тесты (граничные случаи: новые/исчезнувшие категории, нули, пустые периоды, дубли строк).
4. **Дашборд и визуализация:** таблицы с фильтрами и сортировкой, круговые диаграммы, stacked bar, план-факт, экспорт PNG.
5. **AI:** клиент Ollama, шаблоны промптов, админка настроек, сохранение анализов.
6. **Отчёты и админка:** PDF/Excel, email, история, журнал аудита, управление пользователями.
7. **Финализация:** seed-скрипт с демо-данными, README, прогон всех тестов.

## 12. Демо-данные (seed)

Три организации по персонам, по 2+ квартала факта и бюджет:
- Дистрибьютор кормов: «Сухой корм», «Влажный корм», «Лакомства», «Ветеринарные диеты».
- IT-компания: «Серверы CPU», «RAM», «SSD», «GPU», «Сеть», «Лицензии».

Данные должны содержать все типы изменений (рост, снижение, новая, исчезнувшая, без изменений) и перерасходы бюджета. По одному пользователю каждой роли в каждой организации.

## 14. Уточнения (согласовано 03.10.2026, имеют приоритет над текстом выше)

1. **Прототипа `legacy/` нет** — парсинг файлов, синонимы колонок и графики пишутся с нуля.
2. **Руководитель может всё** — его права совпадают с правами администратора (матрица в `app/permissions.py`).
3. **Данные хранятся в разрезе дней**, а не месяцев. В аналитике выбирается детализация: дни, месяцы, кварталы, годы или произвольный диапазон дат. Если во входной строке период указан месяцем или кварталом, запись ставится на первый день периода и помечается исходной детализацией (`grain` = `month`/`quarter`); сумма по дням не размазывается.
4. **Сотрудник и сопоставление статей:** загрузка с неизвестными статьями получает статус «ожидает сопоставления» и не участвует в расчётах, пока руководитель или администратор не сопоставит статьи.
5. **Повторная загрузка факта** заменяет факт за те календарные месяцы, которые есть в файле; прежние версии остаются в истории. Ручной ввод добавляется к данным.
6. **Версия бюджета** — цельный снимок; план-факт берёт последнюю или выбранную версию.
7. **Организации** создаются командой `create-admin --org "Название"`.
8. **Суммы** — одна валюта (рубли), точность до копеек. Отрицательные суммы допустимы в факте (сторно), запрещены в бюджете.
9. **План-факт при нулевом плане:** процент отклонения — «н/д», флаг перерасхода ставится, если факт больше нуля.
10. **Зависимости:** `venv + requirements.txt`; PDF — ReportLab; PNG — kaleido 0.2.1 с plotly 5.x.
